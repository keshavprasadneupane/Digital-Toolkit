# Alembic Cheat Sheet

**Database migrations with SQLAlchemy**

A practical reference for initializing Alembic, generating migrations, applying schema changes, rolling back revisions, and managing migration history in Python applications.

This guide covers synchronous and asynchronous SQLAlchemy projects using standard Python environments or `uv`.

## 1. Initialize Alembic

### Standard SQLAlchemy project

```bash
alembic init alembic
```

### Asynchronous SQLAlchemy project

```bash
alembic init -t async alembic
```

For projects using `uv`, prefix commands with `uv run`:

```bash
uv run alembic init -t async alembic
```

- `alembic init alembic` creates a standard synchronous migration environment.
- `alembic init -t async alembic` creates an environment configured for asynchronous SQLAlchemy engines.

Initialize Alembic only once per migration environment. If the environment already exists, configure it rather than initializing it again.

## 2. Create Migrations

### Autogenerate a migration

Generate a migration by comparing SQLAlchemy model metadata with the current database schema:

```bash
alembic revision --autogenerate -m "describe schema change"
```

Examples:

```bash
alembic revision --autogenerate -m "create users table"
alembic revision --autogenerate -m "add email column"
alembic revision --autogenerate -m "add index to username"
```

Autogeneration requires Alembic to access the application's SQLAlchemy metadata through `target_metadata` in `env.py`.

**Important:** Autogenerated migrations are not guaranteed to be correct. Review every generated migration before applying it. Alembic may not reliably detect table or column renames, data transformations, and certain database-specific changes.

### Create a manual migration

```bash
alembic revision -m "describe schema change"
```

Manual migrations are useful for data transformations, custom SQL, and schema changes that Alembic cannot reliably detect.

## 3. Apply Migrations

### Upgrade to the latest revision

```bash
alembic upgrade head
```

Applies all pending migrations along the path to the current migration head.

### Upgrade one revision

```bash
alembic upgrade +1
```

Applies the next revision along the selected migration path.

### Upgrade to a specific revision

```bash
alembic upgrade <revision_id>
```

Upgrades or downgrades as necessary to reach the specified revision, depending on the current database revision and the migration graph.

### Upgrade to the base revision

```bash
alembic upgrade base
```

This command is not a meaningful way to undo migrations: `base` represents the starting point before any migration revisions have been applied. Use `alembic downgrade base` to reverse the migration history.

## 4. Roll Back Migrations

### Downgrade one revision

```bash
alembic downgrade -1
```

Reverts the most recent revision on the applicable migration path.

### Downgrade to a specific revision

```bash
alembic downgrade <revision_id>
```

Reverts migrations until the specified revision is reached.

### Downgrade to the base revision

```bash
alembic downgrade base
```

Reverts all applied revisions along the applicable migration path.

Downgrading executes the migration files' `downgrade()` functions. Depending on the migration, this can drop tables, remove columns, or destroy data.

**Best practice:** Review downgrade operations and back up important data before rolling back a production database.

## 5. Inspect Migration Status

### Show the current database revision

```bash
alembic current
```

### View migration history

```bash
alembic history
```

Show detailed history:

```bash
alembic history --verbose
```

### Show migration heads

```bash
alembic heads
```

Displays the current head revisions in the migration history. Multiple heads can exist when the migration graph has branched.

### Show migration branches

```bash
alembic branches
```

### Inspect a specific revision

```bash
alembic show <revision_id>
```

These commands help identify which migrations have been applied, which revisions are available, and whether the migration history has diverged.

## 6. Preview SQL Without Applying Changes

Generate SQL for an upgrade without executing it against the database:

```bash
alembic upgrade head --sql
```

Preview a specific revision range:

```bash
alembic upgrade <start_revision>:<end_revision> --sql
```

This is useful for reviewing database changes before execution.

**Note:** Offline SQL generation has limitations. Operations that require live database information or execution-time results may not work in offline mode. Support also depends on the database dialect and migration operations.

## 7. Typical Migration Workflow

### Step 1: Create or modify a model

For example, a SQLAlchemy 2.0 declarative model:

```python
from sqlalchemy import String
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base


class User(Base):
    __tablename__ = "users"

    id: Mapped[int] = mapped_column(primary_key=True)
    username: Mapped[str] = mapped_column(String(100))
```

`Base` represents the application's declarative base.

### Step 2: Generate a migration

```bash
alembic revision --autogenerate -m "create users table"
```

### Step 3: Review the generated migration

Migration files are usually stored in:

```text
alembic/
├── env.py
├── versions/
│   └── <revision_id>_create_users_table.py
└── script.py.mako
```

Inspect the generated `upgrade()` and `downgrade()` functions. Verify table definitions, constraints, indexes, foreign keys, and data migration logic.

### Step 4: Apply the migration

```bash
alembic upgrade head
```

### Step 5: Verify the current revision

```bash
alembic current
```

Repeat this workflow whenever a database schema change is needed.

## 8. Important Alembic Files

A typical setup contains:

```text
project/
├── alembic/
│   ├── env.py
│   ├── versions/
│   └── script.py.mako
├── alembic.ini
└── ...
```

| File or directory | Purpose |
|---|---|
| `alembic.ini` | Main configuration, including the migration script location and other settings |
| `env.py` | Configures database connectivity, metadata, and migration execution |
| `versions/` | Stores individual migration files |
| `script.py.mako` | Template used to generate new migration files |

### `env.py` vs. `script.py.mako`

These files serve different purposes:

- **`env.py`** configures how Alembic connects to the database, discovers SQLAlchemy models, and executes migrations.
- **`script.py.mako`** determines the initial contents of newly generated migration files, including standard imports and revision functions.

Understanding this distinction is especially important when using custom SQLAlchemy types.

## 9. Configure SQLAlchemy Metadata

Alembic needs access to the application's model metadata to detect schema changes.

In `env.py`, the configuration commonly looks like this:

```python
from app.database import Base

target_metadata = Base.metadata
```

Replace `app.database` with the actual module containing your declarative base.

Ensure that all relevant model modules are imported before autogeneration runs. Otherwise, Alembic may not detect all tables.

For asynchronous projects, the async template handles migration execution through an asynchronous SQLAlchemy engine. The database URL, engine configuration, and metadata imports must still be configured correctly.

## 10. Custom SQLAlchemy Types and Application Imports

If your SQLAlchemy models use custom classes, such as custom column types or `TypeDecorator` implementations, generated migrations may need to import those classes.

For example, an application might define a custom type:

```python
# app/db/types.py

from sqlalchemy import String
from sqlalchemy.types import TypeDecorator


class CustomType(TypeDecorator):
    impl = String
    cache_ok = True
```

A model can then use that type:

```python
from sqlalchemy.orm import Mapped, mapped_column

from app.database import Base
from app.db.types import CustomType


class Example(Base):
    __tablename__ = "examples"

    id: Mapped[int] = mapped_column(primary_key=True)
    value: Mapped[str] = mapped_column(CustomType())
```

If Alembic generates a migration that references `CustomType`, the migration must be able to import it.

### Add recurring imports to `script.py.mako`

Open:

```text
alembic/script.py.mako
```

If generated migrations need to reference classes exposed by your application package, you can add an appropriate import to the template.

For example:

```python
from alembic import op
import sqlalchemy as sa
import app

${imports if imports else ""}
```

The standard template contains additional generated content, including revision metadata and migration functions. Keep that content intact and add only the imports you need.

**Important:** `import app` only imports the package. It does not automatically expose every class defined in its submodules.

For example, if a migration references `CustomType`, it may need:

```python
from app.db.types import CustomType
```

Alternatively, the package can explicitly expose the class, provided the generated reference matches that import path.

### When should you modify `script.py.mako`?

Modify the template when the same additional imports should be included in future migration files.

For one-off imports, add the necessary import directly to the generated migration file.

Alembic also supports custom type rendering through `render_item` and `user_module_prefix` configuration. These options are useful when custom types need consistent, explicit rendering.

### Make sure the application is importable

Python must be able to locate your application package when Alembic runs.

Depending on the project structure, this may require installing the package in the active environment or running commands from the appropriate project directory.

For example:

```bash
uv run alembic revision --autogenerate -m "add custom type"
```

### Keep historical migrations working

Existing migration files may import custom application classes when they execute. Moving or renaming a custom type can therefore break older migrations.

Best practices:

- Keep custom types importable for as long as historical migrations depend on them.
- Review generated imports and migration code.
- Avoid importing the entire application if doing so triggers unnecessary initialization or circular imports.
- Prefer stable modules for shared database types.
- Test migrations against a clean database as well as an existing database.

**Rule of thumb:** If a migration references a custom class, ensure that the migration imports that class from a valid, stable module.

## 12. Best Practices

- **Review every autogenerated migration.** Renames, data transformations, and some database-specific changes may not be detected correctly.
- **Keep migrations in version control.** Migration files define the history needed to reproduce database schemas.
- **Use descriptive messages.** Prefer `add_email_to_users` over `update_schema`.
- **Test upgrades and downgrades.** Verify expected schema changes and rollback behavior.
- **Avoid editing migrations that have already been shared or deployed.** Create a corrective migration instead.
- **Keep migration histories consistent.** Multiple independent revision heads should be handled deliberately.
- **Protect production data.** Review destructive operations and maintain appropriate backups.
- **Keep credentials secure.** Avoid committing database passwords or secrets to configuration files.
- **Run migrations as a controlled deployment step.** Avoid concurrent schema migrations from multiple application workers.
- **Keep custom types importable.** Historical migrations may depend on their import paths.
- **Test against a clean database.** A fresh migration run helps reveal missing imports and incomplete migration history.

## Quick Reference

The four commands most frequently used during everyday development are:

```bash
# Generate a migration
alembic revision --autogenerate -m "describe change"

# Apply migrations
alembic upgrade head

# Roll back one revision
alembic downgrade -1

# Check the current database revision
alembic current
```

Use `uv run` before these commands when the project uses `uv`.

**Remember:** Model changes, migration generation, and migration execution are separate steps. Update your models, generate and review a migration, and then apply it to the database.
